## 数据模型复用结论

### 2026-10-31：数据库 V1 → V2

- 已实现：账户新增 `account_type`（默认 `cash`）和 `is_active`（默认启用）；分类新增 `icon_key`（默认 `default`）和 `is_active`（默认启用）。`default` 是供后续界面使用的安全占位标识，当前页面不读取图标。
- `schemaVersion` 升至 2。V1 升级使用 Drift `addColumn` 在事务内添加四列，不删除或重建表；其他未定义升级路径继续显式失败。
- 迁移测试先创建、填充并关闭独立 V1 SQLite 文件，再用 V2 应用数据库打开升级，检查旧 ID、金额、日期、账户和分类引用、备注、新列默认值及外键完整性。
- 本次验证：`dart run build_runner build --delete-conflicting-outputs` 成功（该参数已被 build_runner 忽略）；`flutter analyze` 无问题；`flutter test` 全部 12 项通过；`flutter build apk --debug` 成功。尚未在实际设备上用已有安装数据验证升级。
- 账户/分类管理界面、停用选择规则、转账、退款及余额计算仍未实现。

### 账户、分类与交易后续设计（待实现）

- 计划将数据库从 v1 升至 v2：账户增加类型和启用状态；分类增加图标标识和启用状态。旧账户和分类迁移后默认启用，旧账户默认为现金类型；保留原有 ID、余额、分类与全部交易。
- 默认账户可保存在已有 `app_settings` 表中。迁移或读取时选择已有的有效账户作为回退；停用当前默认账户前需要选择新的有效默认账户，至少保留一个有效账户。
- 余额按整数分计算：初始余额 + 收入 - 支出 - 转出 + 转入 + 退款，忽略软删除交易；禁止跨币种转账，退款币种和账户须符合原支出规则。
- 转账使用一条 `transfer` 记录，`account_id` 为转出账户、`target_account_id` 为不同的转入账户，不计入收入或支出。
- 退款使用 `refund_of_id` 关联有效原支出；以退款实际日期冲减原分类支出，不能超过原支出减去已退款金额。允许多次部分退款；同一操作使用稳定幂等键防重复提交，校验与写入必须同一事务完成。编辑或删除已关联退款的支出需要明确保护规则，避免产生孤立或超额退款。
- 已停用账户和分类保留历史引用及历史显示；新增账目不可选用停用项，编辑历史账目时须明确处理原停用引用。迁移需要 v1 数据库升级测试和历史账目查询测试。

以下为 2026-10-23 手动记账阶段的历史记录，当时没有修改表结构：

- `schemaVersion` 保持为 `1`。
- 不需要 migration，也没有清空或重建用户数据库。
- `amount_minor` 继续使用整数最小货币单位；界面字符串通过确定性解析转换为整数分。
- 为 `account_id` 和 `target_account_id` 补充了不同的 Drift `@ReferenceName`，只修复生成器反向关系命名冲突，不改变数据库 schema。

## 已知风险与下一步

- 数据库列目前没有金额非负、交易类型枚举等 SQLite `CHECK` 约束，主要依靠 Repository 校验。若以后补充约束，必须升级 schemaVersion、实现保留数据的 migration，并增加 v1 旧库升级测试。
- 当前月份在 Provider 创建时取值。App 跨月持续不重启时，统计周期不会自动切换；下一步可增加日期时钟 Provider 或生命周期刷新。
- 模拟器系统日期比当前日期慢一天，日期边界验收前应同步时间。
- 下一步优先补账户/分类管理、余额计算，以及 `transfer`、`refund` 的确定性规则和迁移设计。
